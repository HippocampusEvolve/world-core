# world-core

Общее ядро миров [find-the-end.fun](https://find-the-end.fun). Здесь живёт то,
что у всех миров одинаково и что не знает ни про один из них: контроллер от
первого лица и процедурные материалы. Сюжета в ядре нет и не будет - он
остаётся в приватном репозитории витрины.

| Часть | Состояние |
|---|---|
| [`src/materials`](src/materials) - процедурные карты и материалы | готово |
| `src/core` - тело, взгляд, пружина, риг инструмента, руки, звук удара | переезжает из Winter Tower |

## Материалы

Третий путь к предмету, между «слепить в Blender» и «набрать голой геометрией
кодом»: геометрия из примитивов, а поверхность считается кодом. Ни одного файла
текстур в сборке - только генераторы.

```js
import { makeSet, material, boxUV } from 'world-core/materials'

const set = makeSet('rubble')                       // посчитать карты один раз
const mat = material(set, { normalScale: 1.2 })     // материал из них
const g = new THREE.BoxGeometry(w, h, d)
boxUV(g, w, h, d, 0.5)                              // UV в метрах: 1 тайл на 2 м
```

Четырнадцать наборов: брёвна сруба, бутовый камень (холодный и тёплый), тёсаная
кладка (тёплая и холодная), плиты очага, кирпич топки (с сажей и без), половая
доска, тёсаный брус, кора, торцы поленьев, ткань, чугун.

Бут и тёсаная кладка - разные породы кладки, а не два вкуса одной. Бут это
валуны клеточным шумом, границы органические; тёсаная кладка - обтёсанный камень
рядами с перевязкой, сколотыми кромками и узким швом. Её числа сняты с
референса, а не выбраны на глаз (замер и что он поймал - в комментарии
генератора).

Набор карт считается ОДИН раз и раздаётся многим поверхностям: `material()`
клонирует текстуры ради своего числа повторов, и это ничего не стоит - three
держит объект видеокарты в кэше по `source` плюс параметры сэмплера, а `repeat`
и `offset` в ключ кэша не входят.

### Устройство

```
noise.ts       периодический шум: hash2, vnoise, fbm, ridge, worley
shape.ts       мелочь для цвета: smoothstep, mix, add
bake.ts        выпечка карт БЕЗ DOM - отсюда числа берёт проверка
generators.ts  сами материалы и рецепты (размер, рельеф, тайлинг)
textures.ts    единственное место, где есть three и канва
uv.ts          UV в метрах: boxUV, planeUV, cylinderUV, quadGeometry
```

Разрез между `bake.ts` и `textures.ts` - не косметика. Правило проекта:
геометрию и материал проверяем счётом, браузером последним. Оно выполнимо
только когда карты считаются там же, где считается проверка: на Node, без окна.

### Проверка

    npm run check

Считает все четырнадцать наборов и проверяет 79 утверждений. Меряется три вещи.

**Шов на стыке тайла - точно, без порога.** Генератор это функция от `u = x/S`,
и карта стыкуется сама с собой ровно тогда, когда функция периодична:
`f(1) = f(0)`. Значит её можно просто вычислить при `u = 1`, за краем карты, и
сравнить с `u = 0`. Совпало - шва нет, и это тождество, а не оценка. Меряются
обе карты, которые из функции растут: цвет и высота (разрыв в высоте невидим в
цвете, но карта нормалей строится из неё, и на стыке идёт полоса чужого
освещения).

**Рельеф.** Средний наклон нормали в градусах: ловит материал, приехавший
плоским при зелёных остальных числах.

**Утверждения.** У каждого генератора в комментарии написано словами, каким он
должен получиться («раствор темнее камня», «в камне металла нет вовсе»). Те же
слова записаны неравенством и проверяются вместе с картой.

Порог под материал не подкручивается. Набор, которому стыковаться незачем,
объявляется таким в рецепте - поимённо и с причиной; таких два, и оба видно в
отчёте.

**Замер, подогнанный под материал, ничего не мерит.** Утверждение «кладка идёт
рядами» переписывалось трижды, и первые два раза виноват был прибор. Поиск
локальных минимумов насчитал 66 провалов при четырёх рядах - зерно камня даёт
свои, а отделяет их только сглаживание, шаг которого и становится порогом.
Спектр выглядел строже, но шов это узкий импульс, а у него гармоники 4, 8, 12,
16 равны по высоте: замер показывал то вторую, то шестнадцатую при исправной
кладке. Работает третий вариант, самый прямой: в каждой доле карты самая
непохожая на медиану строка обязана стоять на разделе рядов. Усреднять не по
чему - значит и подбирать нечего.

Зато первый же честный замер нашёл в материале настоящий дефект: сильнее рядов
читалась полосатость, потому что в ряду 3-5 блоков и средняя яркость ряда гуляла
сама по себе. Лечится тем, что тон блока отсчитывается от среднего по своему
ряду.

### Витрина

    npm run build && npx serve .     # дальше /demo/materials.html

Четырнадцать плиток, на каждой набор уложен 3 на 3: стыки видно только там, где
они объявлены. Рядом лежит [`demo/cabin-fireplace.html`](demo/cabin-fireplace.html) -
живой эталон, из которого всё это выросло: зимняя хижина целиком, на r128.

## Что нашлось при переносе

Эталон писался как одностраничная демонстрация и на r128. При переезде в
библиотеку на текущий three нашлись вещи, которых в нём не было видно.

### Карты не стыковались сами с собой

Главное. У всего шума в `noise.ts` есть период решётки, и карта тайлится ровно
тогда, когда множитель координаты совпадает с периодом и оба целые:
`fbm(u * 5, v * 5, 5, 5, ...)` - да, `fbm(u * 5, v * 1.4, 5, 1, ...)` - нет.
В эталоне почти каждый второй вызов был вторым видом. То же с синусами (`|sin|`
имеет период π, поэтому целым должно быть удвоенное число оборотов) и с
индексами ячеек: `hash2(Math.floor(u * 4), ...)` на самом краю даёт доску 4
вместо доски 0.

Прыжок цвета на стыке тайла, из 255:

| набор | было u | было v | стало |
|---|---|---|---|
| брёвна сруба | 37 | 182 | 0 |
| бутовый камень | 0 | 184 | 0 |
| плиты очага | 173 | 173 | 0 |
| кирпич топки | 22 | 42 | 0 / объявлено |
| половая доска | 116 | 25 | 0 |
| тёсаный брус | 0 | 32 | 0 |
| кора дров | 0 | 62 | 0 |
| ткань | 38 | 56 | 0 |

В хижине это не читалось: при свете очага полоса на четырёхметровой стене
выглядит ещё одним пятном копоти. Ловится только счётом.

Правки, изменившие картинку, все здесь: у бревна свиль `v*1.4 → v*1`, волокно
`3.4 → 3.5` оборота, трещины `v*2.4 → v*2`, сучки `v*2.6 → v*3`; у бута камни
`v*3.2 → v*3`; у плит очага `3.4 → 3` по обеим осям; у кирпича рядов `9 → 8`
(нечётное число ломает перевязку на стыке) и индекс столбца через `wrapi`; у
доски коробление `v*1.6 → v*2` и индекс доски через `wrapi`; у бруса
коробление `v*1.2 → v*1`, волокно `3.2 → 3`; у коры хребты `v*2.2 → v*2`; у
ткани переплетение задано числом нитей на тайл вместо шага в пикселях.

### Сажа кверху - это ручка, а не свойство кирпича

У кирпича топки сажа густела к верху карты монотонным градиентом. Для топки
высотой в один тайл это верно, но такая карта не стыкуется по вертикали в
принципе: у монотонного градиента верх с низом не сходится по определению.
Градиент стал параметром: `firebrick(1)` - как в эталоне, `firebrick(0)` -
тайлится в обе стороны. Оба варианта в рецептах, оба под проверкой.

### Замер шва врал, пока был статистическим

Первый заход мерил резкость кромки относительно медианного перепада между
соседними столбцами. Он давал 2-4 «раза» у кирпича и половой доски при
совершенно исправной периодичности - потому что у кладки кромка тайла попадает
ровно на шов раствора, на линию резкую ПО ЗАМЫСЛУ, а медиана считается по сотням
гладких столбцов внутри камня.

Замер заменён на точный (`f(1)` против `f(0)`), и чтобы новый не оказался просто
мягче старого, в проверке ему подсовывают ровно ту ошибку, которая была в
эталоне: индекс доски без заворота. Не поймает - грош ему цена.

### Мерить уклон одного материала бессмысленно

Проверка «кирпич без градиента ровный по высоте» сравнивала среднюю яркость
верхней четверти с нижней и требовала разницы меньше 5%. Получила 13% и была
неправа: в верхней четверти карты всего восемь кирпичей, у каждого свой
случайный тон, и десяток процентов набегает раскладкой. У кирпича С сажей та же
раскладка даёт +13%, у кирпича БЕЗ сажи −13%, и по отдельности оба числа
выглядят одинаково подозрительно.

Случайность у них при этом одна и та же, поэтому спрашивать надо не «ровный
ли», а «что делает ручка»: разницу уклонов, в которой раскладка сокращается. А
что кирпич без градиента и правда ровный, доказывает не эта проверка, а нулевой
шов: у монотонного градиента он нулевым быть не может.

### Цветовое пространство: старая строчка не падает, а молчит

Эталон писал `texture.encoding = THREE.sRGBEncoding`. Этого свойства больше нет:
с r152 цветом заведует `texture.colorSpace`, а константа убрана совсем. Ловушка
в том, что старая строчка не роняет сборку - она заводит на объекте лишнее поле,
которое никто не читает. Базовый цвет уезжает в линейное пространство, картинка
выцветает, и это списывают на тонмаппинг.

Правило: КАРТИНКА - в sRGB, ДАННЫЕ - без цветового пространства. Нормаль,
шероховатость и металл это числа, любая гамма их портит. В `textures.ts` им
проставлен `NoColorSpace` явно, чтобы это было видно глазами, а не держалось на
значении по умолчанию.

### `envMapIntensity = 0` нельзя переносить в библиотеку

В эталоне у каждого материала стоял жёсткий ноль, и стоял правильно: окружения
там не было вовсе. В библиотеке этот ноль молча погасил бы отражения любому
миру, у которого окружение есть, причём симптом выглядел бы как «материал
слишком матовый», а причина лежала бы за три файла. Здесь свойство не трогается,
пока его не попросят.

### Металл без окружения - чёрная дыра, и это арифметика

У металла нет рассеянной составляющей: его базовый цвет это цвет отражения. У
чугуна он 42 из 255, то есть в линейных единицах около 2%. Умножьте на тусклое
небо - получите байт двенадцать, то есть чёрный квадрат. В хижине чугун читался
потому, что рядом горел огонь и на решётке стоял блик, а не потому, что материал
был другим. Вывод для миров: карта металла без карты окружения не работает
(см. бэклог витрины).

### Канва, а не DataTexture

`DataTexture` избавила бы от канвы совсем, но у неё `flipY = false`, а весь
эталон построен на том, что канва переворачивается: у генераторов `v = 0` это
ВЕРХ поверхности. Поднять `flipY` у `DataTexture` мешает неоднозначность в самом
WebGL - `UNPACK_FLIP_Y_WEBGL` надёжно работает для картинок и канвы, а для
сырого буфера ведёт себя по-разному. Проверять это в каждом браузере дороже, чем
оставить канву.

## Подключение

Репозиторий публичный, поэтому игры берут его прямо из git:

```json
"dependencies": {
  "world-core": "github:HippocampusEvolve/world-core"
}
```

Собранный `dist/` лежит в репозитории намеренно: `npm install` у чужого
человека, склонировавшего публичную игру, не должен требовать ни компилятора, ни
сети сверх самого клона. Отсюда правило: **правка в `src/` не считается
сделанной, пока не прогнан `npm run build`** - иначе игры получат вчерашний код.

`three` идёт peer-зависимостью (`>=0.170`): версию выбирает мир, а не ядро.
